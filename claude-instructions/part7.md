### 2026-11-12 — Sprint 27.6: animations that actually run, clock screen, auto dark mode, tagline

**Needs deploying: server + frontend together; no migration** (the new setting keys are plain `app_settings` rows, written on first save).
1. **Animations — root cause.** Since 27.3 the screen-change motion was written as `html[data-vt="forward"] ::view-transition-old(in-main) { … }` (a SPACE before `::`). The view-transition pseudo-elements belong to `<html>` itself, so a selector with a descendant combinator **never matches**: none of my custom keyframes ever ran — only the browser's default cross-fade did, and only a hard refresh (the entrance animation, which was a normal element animation) looked animated. Proved in Chrome by listing `document.getAnimations()` during Continue: only `-ua-view-transition-*` animations, no `in-arrive` / `in-leave`. **Fix, by design:** screen changes no longer use the View Transitions API at all. `withTransition(update, 'forward'|'back')` now (a) sets `data-leave` on `.in-layout` — the current screen melts away in 0.24 s (`in-leave`: fade + shrink + blur), (b) applies the state / route change after `LEAVE_MS`, (c) the new screen mounts with `.in-enter` and arrives like the splash (`in-fade-up`: blur → clear, scale up, rise, staggered; **`in-fade-down` when going back**, via `data-nav-dir` read once at mount → `.in-from-back`). Plain CSS animations: they work in every browser and cannot be skipped. Double taps during the leave are ignored; reduced motion, no animation support, or no screen mounted = immediate. The top bar and background stay still (only the very first screen of a page load animates the top bar: `.in-enter-top`). Verified in Chrome on the production build for all 10 changes (picker → Continue, access → Clock in / Staff / Manager / Developer, every Back to access options, Change property): `in-leave` running at 70 ms, `in-fade-up` / `in-fade-down` running at the arrival, no console errors. The View Transitions API is now only used for the light / dark **circular reveal**, with the selector fixed (`html[data-vt="theme"]::view-transition-new(root)`; that reveal had never run either) and the view-transition names removed.
2. **Clock in / out screen.** The property bar (with "Change property") is gone from this screen; "Back to access options" is at the bottom. On phones and tablets (≤ 1023 px) the card takes all the height that is left and the keypad takes all of the card (`grid-template-rows: repeat(4, 1fr)`, keys grow with the screen, `clamp()` digits; the letters keyboard too), Continue and Back stay in reach. Desktop keeps the two-column card.
3. **Automatic light / dark.** By default the login is **dark from 18:00 to 06:00 and light the rest of the day**, by the device's own clock (`loginTheme.js`: `isDarkAt`, `nextBoundary`, `resolveTheme`). A screen left open flips by itself when the window starts / ends (ONE `setTimeout` to the next change; no polling, no DB). Clicking the logo overrides it **until the next change of the window**, then automatic resumes (stored as `inntrio-login-theme` `{theme, until}`). This replaces 27.5's permanent choice and the App-level `LoginThemeContext` (removed): the login theme no longer writes the in-app `hotelops-theme`, so a browser that was used before is NOT stuck on a saved choice. **Dev setting:** Dev → Platform (the platform-wide settings page) has a new card "Login screen — light / dark": *Automatic by time of day* (default) with "Dark from / until" times, *Always dark*, *Always light*. Keys `login_theme_mode` (`auto|dark|light`), `login_dark_from`, `login_dark_to` (`HH:MM`, start ≠ end) in `app_settings`; served by the public `/api/public-config` (defaults auto / 18:00 / 06:00; invalid stored values ignored); written through `PUT /api/admin/settings` — **dev-only** (`login_` joins the dev-write prefixes: a manager gets 403). The client caches the last config (`inntrio-login-cfg`) so the next load paints in the right theme at once. Existing sign-in screens read it on load; a change applies the next time a screen loads.
4. **Top-bar tagline** never wraps any more: `white-space: nowrap`, and below 760 px the type shrinks with the room beside the logo (container query units on `.in-topnav`: `clamp(5px, (100cqi − 190px) / 29, 11px)`, 9 px max under 420 px). Checked at 390 px and 360 px: one line.
Tests: new `login-theme` (9: window maths incl. wrap-around, next boundary, resolve rules, hook auto-by-clock / click override that expires / server config applied + cached / older server / offline, the single timer to the next change, public-config defaults and validation, dev-only + validated settings PUT, the Dev card), `staffportal` 34 (leave-then-arrive helper incl. double tap / reduced motion / fallbacks, new motion CSS incl. "no space before ::view-transition" and no names, tagline one-line CSS, clock-fill CSS, no property bar on the clock screen, logo switch + override), `login-splash` 7 (entrance classes, first-frame-only top bar, from-back). The login tests that assumed a dark default now pin the theme through the cached config (it depends on the time of day otherwise). Full regression green; build compiles.
**Open:** the "General settings" you mentioned is, in this app, Dev → Platform (there is no page literally called General); say if you wanted it on the Settings page instead. The theme follows the DEVICE clock, not Pacific time — a laptop in another timezone flips at its own 6 pm.

### 2026-11-12 — Sprint 27.4: login — animation bug, top bar, welcome splash

1. **Bug: screens animated twice (transition, then again).** Cause: the staggered fade-up entrance was switched off with `html[data-vt] .in-layout > * { animation: none }` while a view transition ran. When `data-vt` was removed at the end, the rule stopped applying and the CSS `animation` property went from `none` back to `in-fade-up`, which **restarts the animation** on the already-visible screen. Fix: the entrance is now opt-in per mount — `AuthFrame` sets the `in-enter` class ONCE (`useState` initialiser) only if the screen is NOT arriving through a view transition (no `data-vt` at mount), and every entrance rule is scoped to `.in-enter`. Nothing toggles it later, so nothing can restart. I also removed the slow background "drift" animation: each screen mounts its own copy of the scene, so the new copy started from frame 0 and would visibly jump at the end of a transition. Verified in headless Chrome on the production build: after Continue the access screen has no `in-enter` and **0** running `in-fade-up` animations.
2. **Top bar:** back to the plain Inntrio logo (`Inntrio-logo-dark.svg`, 177 px / 128 px) on the left and, on the right, **"HOSPITALITY MANAGEMENT PLATFORM"** in gold small caps (two lines on phones). The tagline-in-logo variant is no longer used (file stays in `public/inntrio/`).
3. **Big centred logo + "PROPERTY OPERATIONS, REFINED" removed** from the picker and the access screen (`Masthead` / `hero` deleted, with the `in-hero` transition name).
4. **"One workspace. Every department." removed.**
5. **Welcome splash** (`Splash.js`, used by `TenantPicker`): when the app opens at the property picker, the Inntrio logo appears alone in the middle (blur + scale in, then the gold "Hospitality management platform" line letter-spacing in), holds 1.5 s, then the picker mounts underneath (its own entrance animation runs) while the splash fades out over 0.7 s — about 2.2 s in total. Tap or any key skips straight to the fade. It plays **once per page load** (module flag — not when you come back to `/` inside the app, e.g. Change property), **never** for the dev property picker, deep links like `/:slug/login` or `?mode=clockin` (kiosk returns), or with reduced motion. Timings are the exported constants `SPLASH_HOLD_MS` / `SPLASH_FADE_MS`.
